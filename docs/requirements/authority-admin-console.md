# Authority Admin Console

## Background

- 当前 Win 端只有单一的 `Permissions` 页面，主要覆盖 authority 角色/权限策略编辑。
- `MyFlowHub-Server` 的 auth 协议已经支持待审批注册、批准/拒绝、permit 签发/撤销，但 Win 端没有对应 GUI 入口。
- 现有权限页把 authority 解析、策略编辑、运行时快照都堆叠在一页里，可读性和可操作性都偏弱。

## Goal

- 将 Win Authority 管理能力重构为一组独立入口，分别覆盖访问策略、注册审批和准入许可签发。
- 提高访问策略页面的可用性，让管理员可以更低成本地理解和修改策略。

## Scope

### Must

- 左侧导航新增一组 Authority 相关入口，分别对应：
  - 访问策略
  - 注册审批
  - 准入许可
- 英文环境下使用全英文名称和说明；中文环境下使用全文中文名称和说明。
- 访问策略页面必须继续支持 authority 解析、policy 加载/保存、运行时角色预览和单节点权限查询。
- 访问策略页面必须改为 tab 结构，至少包含：
  - 当前策略
  - 角色管理
- 访问策略页面在首次加载和手动重新加载 policy 时，都必须给出页面内可见的显式加载提示。
- 默认权限和角色权限都必须通过内置权限目录勾选，不再要求用户手动输入 CSV。
- 注册审批页面必须支持：
  - 查看待审批注册列表
  - 刷新列表
  - 批准单条注册请求
  - 拒绝单条注册请求
- 准入许可页面必须支持：
  - 刷新当前活动 permit 列表
  - 签发 permit
  - 从列表中撤销 permit
  - 展示当前 authority 的活动 permit 列表
  - 在首次加载和刷新期间给出页面内可见的 loading 提示
  - 当解析出的 authority 不是当前登录节点时，显式提示“当前需在 authority 节点本机操作”，并停止继续等待 permit 管理超时

### Optional

- 为待审批列表提供轻量筛选或统计信息，只要不引入新的协议依赖。
- 为最近签发 permit 提供快捷复制或回收操作。

### Out of Scope

- 不修改 `MyFlowHub-Server` 协议。
- 不新增 permit 列表或 permit 查询能力。
- 不自动把 permit token 长期持久化到本地配置。
- 不重构 Home 页登录/注册主流程。

## Scenarios

- Authority 管理员希望在单独页面处理首次注册审批，而不是在调试页或 CLI 中手动发协议。
- 管理员希望快速给指定设备签发一次性准入 permit，并在必要时撤销。
- 管理员希望更容易理解默认角色、角色权限和节点覆盖之间的关系，并安全地保存到 authority。
- 管理员希望先在“当前策略”查看默认准入、节点覆盖和运行时结果，再切到“角色管理”集中维护角色。
- 管理员希望通过列表先浏览角色摘要，再按需进入弹窗维护某个角色，而不是在页面上同时展开所有角色权限。
- 管理员希望默认准入和角色权限都通过“权限列表 + 添加 / 移除”维护，而不是记忆并手动输入权限字符串。
- 管理员希望角色编辑弹窗按单列顺序展示角色名、预设动作和权限列表，不要左右分栏来回扫读。
- 管理员希望新增角色权限时先打开选择列表，再显式把某个 catalog 权限加入角色，而不是直接改写已有权限行。
- 管理员希望保存选项、运行时检查和单节点查询收敛到一个更紧凑的操作面板，而不是三个相互割裂的大卡片。
- 管理员希望注册审批页保持成紧凑待办队列，只在需要时打开单条请求的审阅弹窗，而不是在列表里同时展开批准和拒绝表单。
- 管理员希望准入许可页首屏只保留动作入口和最近结果，不要长期铺开签发 / 撤销大表单。

## Functional Requirements

1. 应用左侧必须出现 3 个独立 Authority 管理入口。
2. 访问策略页面必须支持基于当前 session 的 authority 自动解析，并清楚展示当前登录身份、authority 和运行时校验状态。
3. 访问策略页面必须包含“当前策略”和“角色管理”两个 tab，且默认进入“当前策略”。
4. “当前策略”tab 必须以摘要视图展示 `auth.default_role`、`auth.default_perms`、`auth.node_roles`，其中默认准入详细编辑必须通过弹窗完成。
5. “角色管理”tab 必须以紧凑角色列表展示 `auth.role_perms`，每个角色通过独立编辑动作打开弹窗维护。
6. 默认权限和角色权限必须通过预置权限目录驱动的“权限列表 + 添加 / 移除”交互维护，而不是直接编辑 CSV 字符串或整块矩阵勾选。
7. 角色编辑弹窗必须采用单列布局；已有权限项只读展示，新增权限必须通过弹出的权限选择列表完成。
8. `auth.node_roles` 也必须以紧凑列表展示；新建和编辑节点覆盖时，应通过弹窗维护单条覆盖，而不是在页面上直接铺开输入框。
9. “当前策略”tab 中的保存选项、运行时快照和单节点查询应收敛到同一操作面板，运行时详情默认不必整块展开。
10. 默认准入、节点覆盖和角色管理等主要编辑区域必须在就近位置提供保存入口；这些入口仍保存整份 policy，而不是局部保存。
11. 若已加载策略包含目录外权限，页面必须显式展示并在保存时保留，不能静默丢失。
12. 访问策略页面保存后必须能可选执行持久化、运行时应用、失效广播和运行时校验。
13. 注册审批页面必须以紧凑列表展示每条 pending request 的 `request_id`、`device_id`、申请角色、显示名、创建时间和过期时间，默认不在列表中展开批准 / 拒绝输入区。
14. 注册审批页面必须允许管理员先打开单条 pending request 的聚焦审阅面，再在同一个面板中执行 approve 或 reject。
15. approve 时允许角色留空，由 authority 协议自行决定默认行为；前端不得强行填充默认角色替代空值。
16. 准入许可页面必须把签发动作收敛为按需打开的聚焦操作面，首屏保留动作入口、协议边界提示和活动 permit 列表。
17. 准入许可页面必须允许管理员在签发动作面输入 `device_id`、`role` 和可选过期时间来签发 permit。
18. 准入许可页面必须允许管理员从活动 permit 列表中直接撤销 permit，而不是要求手动输入 token。
19. 当解析出的 authority 不是当前登录节点时，permit 页面必须显式提示“当前需在 authority 节点本机操作”，并停止自动请求 permit 列表。

## Non-functional Requirements

- 复用现有 Win `AuthService`、`ManagementService` 和 authority orchestration 逻辑，不引入不必要的新协议层。
- 页面职责必须清晰，避免把 authority 管理重新堆回单个巨型页面。
- 所有 authority 页面都必须在未连接、未登录、缺少本地身份时显式阻止危险操作。
- 访问策略 UI 必须优先提升信息分层、表单可读性和保存反馈，不仅是把原有字段平移到新布局里。
- 访问策略页的加载反馈必须在页面内可见，不能只退化为按钮禁用或隐藏状态切换。
- 访问策略页不得要求用户手动输入权限 CSV。
- 访问策略页首屏不得继续把默认准入和所有角色权限整页铺开；默认准入和角色详情应按需进入弹窗编辑。
- 角色列表和角色权限列表应保持单行优先的紧凑节奏，避免在角色管理里堆叠高密度多行块状卡片。
- Authority 管理 GUI 不得再暴露手动 authority override 输入或内部解析原因文案。
- 注册审批页不得回退为每条请求常驻展开 approve / reject 双表单；审批详细输入必须收敛到单一审阅弹窗。
- 准入许可页首屏不得长期展开签发 / 撤销大表单；签发输入必须收敛到按需打开的聚焦弹窗。
- 当 authority 为远程节点时，permit 页不得继续以普通失败态或 timeout 伪装成“可远程管理”。
- permit token 默认只保留会话态展示，不在本地配置里长期保存。

## Edge Cases

- authority 无法解析。
- 已有策略中存在目录外权限。
- 角色存在 `*` 且又同时出现普通权限。
- 待审批列表为空。
- approve 的 role 为空字符串。
- reject 的 reason 为空。
- issue permit 时缺少 `device_id` 或 `role`。
- revoke permit 时 token 为空。
- permit 列表为空。
- permit 已被消费 / 撤销 / 过期，因此不再出现在活动列表中。

## Acceptance Criteria

1. 左侧导航中能看到 3 个独立 Authority 管理入口，且中英文环境分别保持全英文 / 全中文文案。
2. 访问策略页面可以完成 load/save policy、runtime 预览和节点权限查询，且交互体验明显优于原版本。
3. 访问策略页面具备“当前策略 / 角色管理”两个 tab，并且默认权限和角色权限不再通过 CSV 文本框编辑。
4. 默认准入、节点覆盖和角色管理附近都能看到保存入口，且这些入口复用同一条策略保存链路。
5. 页面在 policy 加载期间会显示明确的页面内加载提示。
6. 目录外权限在页面中可见，并能在保存时被保留。
7. 注册审批页面可以完成待审批列表查询、批准和拒绝的基础链路。
8. 准入许可页面可以完成 permit 列表刷新、permit 签发与列表行内撤销，并清楚展示活动 permit 列表；在 remote authority 场景下会改为显式限制提示，而不是继续等待超时。
9. 本轮改动要求补齐真实 permit list 协议能力，但不引入 permit 历史持久化。
